# Decisions

Where the spec was ambiguous, or where implementation forced a choice, this file records what was chosen and why. Newest phase at the bottom.

## Phase 1: skeleton

### Backend

| # | Decision | Why |
|---|----------|-----|
| 1 | **Minimal APIs** (replaced by controllers, see #44), organised as endpoint-group extension methods (`MapPlantEndpoints`, `MapSensorEndpoints`). | Less ceremony than controllers for a small surface. Groups keep `Program.cs` readable and give one place per feature. |
| 2 | **Parse and validate in one pass.** The JSON is deserialised into nullable `*Document` classes, then a builder validates and maps them to immutable domain records. | Missing fields become errors with a JSON path (`$.site.floors[0]...`) instead of deserialiser exceptions. All errors are collected at once, so a user fixing a file sees everything that is wrong. |
| 3 | **Unknown properties are errors.** Captured via `[JsonExtensionData]`. | A typo such as `nominalMaxx` would otherwise be silently ignored and the tag would fail validation for the wrong reason, or not at all. |
| 4 | **Ids are lowercase kebab-case** (`r-01.cabinet-temp`) and unique plant-wide for each kind (floor, asset, tag). | Tag ids key the live stream and history API, so they must be globally unique and URL-safe. |
| 5 | **Coordinates:** metres, origin at the floor's corner. `position` is the footprint centre (`x`, `z`) plus an optional base elevation `y`. `rotation` is in degrees around the vertical axis. `shape` is optional and defaults by asset type. | Easiest to author from a floor plan. The validator checks that the rotated footprint stays inside the floor. |
| 6 | **Thresholds:** a nominal band (`nominalMin`/`nominalMax`) plus optional `alarmLow`/`alarmHigh`. Inside the band is *normal*, outside it is *warning*, at or beyond an alarm limit is *alarm*. | The spec names "nominal min/max, alarm thresholds" only. A separate warning band can be added later without breaking files. |
| 7 | **Import is file-based.** The plant file loads at startup and fails fast, listing every error. `POST /api/plant/validate` checks a candidate file without applying it. There is no runtime replace endpoint. | The demo is public. Letting one anonymous visitor swap the plant for everyone is a bad default. Runtime import can come back behind auth. |
| 8 | **2 s sampling** (spec example: 5 s), 24 h retention, **24 h backfilled at startup**. All configurable under `Simulation:*`. | 5 s feels sluggish in a live UI. 24 h × 2 s × 60 tags ≈ 2.6 M samples ≈ 41 MB, which fits Render's free tier. The backfill (about 0.7 s, done before Kestrel listens) means trend charts and Phase 3 trend questions work immediately. |
| 9 | **Simulator:** an Ornstein–Uhlenbeck (mean-reverting) walk around the band centre, plus Poisson-distributed drifts, single-sample spikes and short alarm excursions. Each tag has its own `Random`, seeded from `seed ^ FNV-1a(tagId)`. | Smooth and realistic, with a bounded variance. Per-tag seeding makes a tag's series independent of which other tags exist. FNV is used because `string.GetHashCode` is randomised per process. Development uses seed 42. Production is random unless `Simulation__Seed` is set. |
| 10 | **SSE rather than WebSockets** for live readings. | Traffic is one-way. `EventSource` reconnects on its own, and SSE passes through proxies and CDNs as plain HTTP. Each subscriber gets a bounded channel that drops the oldest batch, so a slow client can't stall the others. |
| 11 | **Sensor payloads use Unix epoch milliseconds** (`ts`, `t`). | Compact, and native to JS `Date` and chart libraries. The plant model uses ordinary JSON. |
| 12 | **History downsampling** by equal-count bucket averages. | Cheap and stable for sparklines and trend charts. Swap in LTTB if peak preservation matters later. |
| 13 | **`TimeProvider`** is injected for all clocks. | Makes the hosted service and store testable with `FakeTimeProvider`. |

### Frontend

| # | Decision | Why |
|---|----------|-----|
| 14 | **No state-management library.** Live readings live in a small external store read via `useSyncExternalStore`; plant and selection live in a React context. | The state is small. This avoids a dependency, and components re-render only for the tags they read. |
| 15 | **Status is computed server-side per tag.** The UI only rolls statuses up (worst of). | One source of truth for threshold logic. |
| 16 | **3D labels are a projected DOM overlay** (`SceneLabelRegistry`), not drei `<Html>`. | drei `<Html>` creates a React root per label. Under React 19 StrictMode these roots crashed with `removeChild` errors when a floor unmounted. The overlay is ordinary React, positioned with transforms in `useFrame`. |
| 17 | **Selection is shown with accent edges plus a footprint pad**, not drei `<Outlines>`. | Inverted-hull outlines were invisible at plant scale in world units and produced artefacts in screen-space mode. Edges plus a pad read clearly from any angle. Status keeps the emissive tint, as the spec asks. |
| 18 | **Contrast adjustments to the palette** (WCAG AA, measured): `--text-muted` is `#736356` instead of `#7A6A5D` (4.42:1 on `--surface`). Accent-coloured text and primary buttons use `--accent-hover`/`--accent-text`. Status text uses darker `*-text` variants. | The spec colours stay as the tokens for fills, rings, dots and the 3D scene. Only text pairings that failed AA were changed. |
| 19 | **Fonts are self-hosted** via `@fontsource-variable` (Inter, JetBrains Mono). | No third-party font requests, and it works offline and on GitHub Pages. |
| 20 | **Dev uses the Vite proxy** for `/api`. Production uses `VITE_API_BASE_URL`. | The browser sees a single origin locally, so no CORS setup is needed for development. |

### Data

| # | Decision | Why |
|---|----------|-----|
| 21 | Sample refrigerators use the manufacturer **"Generic"**, and the demo manual is a fictional document written for this project. | Real vendors' manuals are copyrighted and not needed to show the RAG flow. The file name `Generic-refrigeration-demo-manual.pdf` carries the manufacturer, so the plant's manufacturer matches it. |

## Auth

| # | Decision | Why |
|---|----------|-----|
| 22 | **Users live in PostgreSQL** (`users`: username, password hash, role), hashed with ASP.NET Core `PasswordHasher`. The only seeded user is `guest` / `guest` (role `guest`), created at startup if missing. There is no admin user. | No hardcoded credentials in code paths. Without an `admin` user, the tenant create/edit/delete endpoints (admin policy) are unreachable until one is added to the table. |
| 23 | **Users are not tied to a tenant.** | Auth had no tenant concept before. Every signed-in user sees all tenants' sites. |

## Phase 2: RAG

| # | Decision | Why |
|---|----------|-----|
| 24 | **`ManualVectorStore`** wraps the official `Qdrant.Client` (gRPC, port 6334). Payload: `text`, `source_file`, `page`, `document_hash`, and optional `manufacturer`, `model`. Cosine distance. | Ingestion can skip a document whose hash is already stored, and search can filter by the selected asset's manufacturer/model. |
| 25 | **One shared collection, no tenant filter.** | Manuals are global files in `data/manuals`, not per tenant. |
| 26 | **Vector size is config** (`Qdrant:VectorSize`, default 1536). | It must match the embedding model, which is not chosen yet. |
| 27 | **OpenRouter over plain `HttpClient`** (`OpenRouterClient`): embeddings and streamed chat completions, no SDK. The key comes from `OpenRouter:ApiKey` only. | The API is small and OpenAI-compatible, so an SDK adds nothing. |
| 28 | **Ingestion is a hosted service** that logs and skips when the folder is empty, the key is missing or Qdrant is down. A document is skipped when its SHA-256 is already stored. Text is read per page with PdfPig, chunked at about 450 words (about 600 tokens) with 60 words of overlap, and chunks never span pages. | The API must start without the optional pieces. Per-page chunks keep one page number per citation. A document that failed halfway is not retried, because its hash is already stored for the chunks that got in. |
| 29 | **Manufacturer and model come from the file name**, matched against the plant's assets. Retrieval filters on manufacturer only, and widens to an unfiltered search if that finds nothing. | File names rarely carry the full model, and a model filter would exclude most manuals. |
| 30 | **Citations are numbered excerpts.** The prompt numbers the retrieved chunks, the model cites `[n]`, and only cited chunks are sent as source chips. | Avoids listing sources the answer did not use. |
| 31 | **Charts use a fenced `chart` block** (`{"tagId", "minutes"}`) in the answer, not tool calling. The API validates the tag, reads the sensor store (5 to 240 minutes, 120 points) and sends a `chart` event. The UI hides the block. | Works with any chat model and needs no tool-call loop. |
| 32 | **Rate limit:** 10 questions per client address per UTC day, counted in memory, so it resets on restart. A request with `X-OpenRouter-Key` skips the limit and uses that key for the request only. | Matches the spec. The address is the connection's. Behind a reverse proxy it is the proxy's address until forwarded headers are configured (not done, since trusting them would let clients spoof the address). |
| 33 | **Failed model calls still count** toward the daily limit. | Keeps the counter simple. |
| 34 | **Chat is a POST streamed with `fetch`**, not `EventSource`. The user's own key is held in component state only. | `EventSource` cannot POST or send headers. |
| 35 | **The Group level is gone, and "equipment" is now "asset".** The hierarchy is Site → Floor → Asset → Tag (`floors[].assets[]` in the JSON, `assetId` in the chat request). The 3D view no longer draws group zones or group labels, and the asset panel and notifications show the floor only. | Groups added a level that the interface used only for labels. Assets, the unit users select and ask about, now sit directly under a floor. |
| 36 | **Stored sites in the old format stop the API at startup with a clear message** that points to the one-off SQL in `docs/plant-config.md`. | Silently skipping a site would hide it from the catalogue and the simulator. |
| 37 | **All relational access goes through the Repository pattern on Entity Framework Core** (Npgsql provider). `IUserRepository` and `ITenantRepository` live in Core, their EF Core implementations and the `SensorMindDbContext` in Infrastructure; endpoints, seeding and `PlantCatalog` use only the interfaces. The tenant's site config stays one text column (`sites.config_json`). Qdrant, the in-memory sensor store and OpenRouter are not part of this. | One data-access style instead of hand-written SQL, and Core stays free of database code. The repositories keep the operations the app already used (find or add user, list, save and delete tenant), so nothing was added speculatively. |
| 38 | **Schema comes from one EF Core migration, applied at startup.** Its SQL is `CREATE TABLE IF NOT EXISTS` with the DDL the app used before EF Core, so a database created by the earlier code is baselined (the history row is added, nothing is changed or lost) and a fresh one is created. EF Core's foreign-key index on `sites.tenant_id` is not created, to leave existing tables as they were. | Existing dev databases keep working without a manual step. Later schema changes are ordinary `dotnet ef migrations add` migrations. |

| 39 | **Swagger (Swashbuckle) is served in Development only**, at `/swagger`. Endpoints that need login get the Bearer lock through one operation filter (all except `AllowAnonymous`), mirroring the fallback policy. | Lets the API be explored and called from the browser without exposing its structure in production. The filter avoids repeating a requirement on every endpoint. |

| 40 | **Toasts are a small in-house store** (`state/toastStore.ts`, rendered by `ToastProvider`, read through `useToast`), no library. The API client raises them for every failed call and maps the status to a fixed friendly sentence (network, 400, 401, 403, 404, 429, 5xx). Server text is never shown. | The client is not a React component, so the store is callable from it. Fixed sentences cannot leak internals. The same message arriving again restarts the timer instead of stacking, so a failing poll cannot flood the screen. |
| 41 | **A failure is shown once.** Toast by default. No toast where the screen already shows it: the chat panel and the plant-load error screen (calls marked `quiet`), and 422 validation lists in the tenant editor. The old inline text on the login form and in the tenant modal is removed. Silent background calls (history, validate, chat status) stay silent. A 401 on a signed-in call still signs the user out, with a toast. | Two copies of one error is noise. A toast needs no layout space on the login page or in the modal. |
| 42 | **Unhandled exceptions return a generic 500 problem response** (`RequestLogMiddleware`, which replaces `UseExceptionHandler`): a fixed title, no detail, no exception text. The exception is written to the console log only. | The client gets JSON it can map, and nothing internal leaves the server. |
| 43 | **Request log table `logs`** (`id` identity, `timestamp_utc`, `type` SUCCESS/FAILURE, `status_code`, `method`, `path`, `logged_in_user`, `error_message`), written by the same middleware after the response is sent, through `ILogRepository`. Logged: every 4xx/5xx response, plus successful writes (login, tenant create/edit/delete, chat). Not logged: successful reads (live feed, history, plant, sites, health) and tenant validate. Never stored: bodies, query strings, the chat question, headers, passwords, tokens or keys. `logged_in_user` is the signed-in name, or the attempted name for a login (set through `HttpContext.Items`), empty for other anonymous calls. `error_message` is a fixed reason (HTTP reason phrase, `Wrong username or password`, the chat's friendly error, or `Unhandled <ExceptionName>`), cut at 500 characters. | The reasons are generic by construction, so no secret can reach the table. A failed write is a console warning only and never affects the request. A chat stream that fails after it started is stored as FAILURE with status 200, because the HTTP status was already sent. No retention or UI yet: read it with SQL, e.g. `select * from logs order by id desc limit 50;`. |
| 44 | **Controllers instead of minimal APIs.** One `[ApiController]` per group in `SensorMind.Api/Controllers` (`AuthController`, `PlantController`, `ReadingsController`, `SitesController`, `TenantsController`, `ChatController`), with the same routes, status codes and JSON as before; they receive the repositories and services by constructor injection. `Program.cs` calls `AddControllers` and `MapControllers`. Form value providers are removed (bodies are JSON or raw text, and a form read would consume them), and the `traceId` that MVC adds to problem responses is stripped so error bodies stay as they were. | The team prefers the controller style. The one visible difference is that an empty or malformed request body now returns a 400 problem response (it used to end in a generic 500). |
| 45 | **Warnings and alarms pulse; nothing strobes.** Warning is a slow amber pulse (0.8 Hz), alarm a stronger, wider red pulse (1.6 Hz), both smooth sine/ease-in-out and far below 3 flashes a second. The periods are CSS tokens (`--pulse-warning`, `--pulse-alarm` in `index.css`) read by the CSS glow (status dots in the tree, floor tabs and panels, the bell and its badge) and by the 3D scene, which animates only flagged meshes' emissive intensity in `useFrame` on the material (no React state per frame). The bell takes the worst unread severity. With `prefers-reduced-motion` nothing animates: dots and bell get a fixed ring and flagged meshes a fixed bright tint plus an outline. | Status must be hard to miss without being a seizure risk. Speed (and the text labels, which stay) separates warning from alarm, so colour is not the only cue. One token pair keeps 3D, tree and bell in step. |
| 46 | **The legend is a static key; the units themselves pulse colour and glow.** `StatusDot` takes `still`, used by the 3D legend (`SceneLegend`), so its Normal/Warning/Alarm dots never animate; the dots that report a real status (tree, floor tabs, sensor panel) and the bell still pulse. In the scene a flagged unit pulses three things from one sine in `useFrame` (warning 0.8 Hz, alarm 1.6 Hz, from #45's tokens): its body colour towards the status colour (up to 70% warning, 85% alarm), its emissive intensity (up to 0.8 / 1.6) and a slightly larger additive glow shell in the status colour (opacity up to 0.4 / 0.65). The selected or hovered outline is unchanged and sits on top; normal units stay static. With `prefers-reduced-motion` the same three are held at a fixed strong tint (70%, 0.8, 0.35) plus the status-colour outline. | #45 pulsed only a faint emissive on a grey body, which was not visible, while the legend, a key, was what blinked. A shell mesh is cheaper and simpler than a post-processing glow for about twenty units. |
| 47 | **The right column is a `SplitColumn`** (`components/layout/SplitColumn.tsx`): two sections with header-button collapse (`aria-expanded`/`aria-controls`) and a splitter (`role=separator`, pointer capture, arrow keys, Home/End, double-click resets to 60/40). The split is a flex-grow ratio, so each open section keeps a 140 px minimum and a collapsed one shrinks to its 40 px header while the other takes the space. Collapsed bodies stay mounted (`inert`), so chat history survives. State is stored per browser in `localStorage` (`sensormind.split.right`: `{ratio, collapsed}`). The asset name and status badge moved from the sensor body into its header bar, and the free-questions badge from the chat header to the line above the input. | Panels behave like VS Code with no dependency and nothing but CSS to clamp on window resize. The status stays visible when the sensor section is collapsed. |
| 48 | **Request logs are viewable without sign-in.** `GET /api/logs` (`LogsController`, `[AllowAnonymous]`, Swagger tag Logs) filters by `type`, `statusCode` or `statusClass`, `method`, `path`/`user`/`message` (contains, case-insensitive, `ILIKE` with wildcards escaped), `from`/`to` (UTC, with `Z`) and pages newest first (`page`, `pageSize` default 50, max 200) through `ILogRepository.Query`, server-side in EF Core. The UI page `/logs` (`components/requestlog`) is chosen in `main.tsx` before `App`, so it needs no router, never checks the session and cannot trigger the sign-out handler; its API call sends no token. Filters live in the URL query string. Successful GET, HEAD and OPTIONS (CORS preflight) requests are not logged, so the list never logs itself and cross-origin deployments do not fill the table with preflights; a 4xx on `/api/logs` is logged like any other. No index was added. | The table is meant to be looked at, and the user asked for no authentication. It exposes usernames (including attempted ones), paths and messages to anyone who can reach the API, so it should be put behind auth or removed before a public deployment. Ordering by `timestamp_utc` scans and sorts the table, which is fine for demo volumes; `create index on logs (timestamp_utc desc, id desc)` is the fix if it grows. On a static host such as GitHub Pages a direct load of `/logs` needs a 404 fallback to `index.html` (the links work in-app). Folder is `requestlog`, not `logs`, because `frontend/.gitignore` ignores anything named `logs`. |
